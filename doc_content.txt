1. Executive Summary
The platform will provide invoicing, purchases, customer and supplier ledgers, inventory, VAT reporting, financial statements, POS operations, offline working, and future UAE e-invoicing integration. The recommended launch architecture is a modular monolith with strict domain boundaries, PostgreSQL as the system of record, and an offline-first client architecture for mobile and desktop.
Build financial correctness before convenience features. Every posted financial transaction must create balanced journal entries.
Treat the invoice as structured data. PDF, thermal receipt, and e-invoice XML are separate renderers of the same canonical invoice object.
Start with a modular monolith, not microservices. Extract services only when scale or operational boundaries justify it.
Use Flutter for mobile and desktop POS; use React/Next.js for the accountant and administration dashboard.
Use PostgreSQL with tenant isolation, NUMERIC money fields, immutable posted entries, audit logs, and database-level integrity constraints.
Keep UAE compliance rules configurable. Final legal and tax validation must be completed with a UAE tax adviser before production launch.

4.1 Architecture Principle
The backend is deployed as one application initially, but each business domain must be implemented as an isolated NestJS module. A module may access another module only through an application service interface or published domain event. Direct cross-module table writes are prohibited.

6.1 Accounting Integrity Rules
Every posted source document creates exactly one balanced journal entry or a defined set of linked journal entries inside one database transaction.
SUM(debit) must equal SUM(credit) before commit. Enforce this through the posting service and a deferred database constraint trigger.
Posted journal entries cannot be edited or deleted. Corrections use reversal entries and corrected replacement documents.
Invoice lines store the tax calculation snapshot used at posting time; later tax configuration changes must not rewrite history.
Closing a fiscal period blocks posting into that period except through an explicitly authorized reopening process.
All money fields use NUMERIC with an agreed scale. Store transaction currency, exchange rate and base-currency values when multicurrency is introduced.

7. Invoice Lifecycle and State Machine
DRAFT  | validate + reserve posting request  vREADY_TO_POST  | atomic posting transaction  vPOSTED -------> PARTIALLY_PAID -------> PAID  |                    |  |                    +------ payment allocation / reversal  |  +------> E_INVOICE_PENDING -> ACCEPTED / REJECTED  |  +------> CREDIT_NOTE_ISSUED / REVERSEDRules:- A posted invoice is immutable.- Cancellation after posting creates an accounting reversal or credit note.- PDF regeneration never changes financial data.- External e-invoice retries are idempotent.
7.1 Invoice Numbering
Offline clients should not permanently assign the final legal invoice number unless they have a preallocated branch/device numbering range. The safest default is to create a local draft reference and allocate the final sequential number during server posting. Number allocation must use an atomic database lock or sequence strategy and must never use MAX(number)+1.
8. Offline-First Sync Architecture
Client write -> Local SQLite transaction -> Local Outbox -> Background Sync     -> POST /sync/push with idempotency key     -> Server validates tenant, permissions and business rules     -> Server commits or returns structured conflict     -> Client stores server version and advances sync cursor     -> GET /sync/pull?cursor=... for incremental changes
Record Type
Conflict Strategy
Draft notes and non-financial preferences
Last-write-wins may be acceptable
Party and item master data
Version check; merge safe fields or request user selection
Invoices, payments and journal-affecting data
Never silently overwrite; reject or send to reconciliation queue
Stock movements
Server validates available stock and movement sequence; conflict requires review
Numbering collision
Server assigns final number or rejects preallocated range violation
Use client-generated UUIDs, device_id, client_created_at, server_updated_at and row_version.
Every mutation request carries an idempotency key so retries cannot duplicate invoices or payments.
Incremental pull uses a server-generated cursor, not only client timestamps.
Sync status must be visible to users: local, syncing, synced, attention required.
Provide manual Sync Now and a conflict resolution screen for authorized roles.

10. UAE VAT and E-Invoicing Readiness
The application must separate tax calculation, invoice rendering and external e-invoice exchange. Compliance rules should be versioned and configurable because implementation details and accredited provider requirements may evolve. Before release, a UAE tax professional must validate invoice fields, VAT mappings, retention rules, credit-note handling and reporting outputs.
VAT categories: standard-rated, zero-rated, exempt and out-of-scope.
Store seller and buyer legal details, TRN where applicable, invoice type, supply date, currency, tax totals and line-level tax information.
Generate VAT reports from posted ledger and invoice snapshots, not from editable drafts.
Define a TaxInvoiceSerializer interface with PDF, thermal and structured XML implementations.
Create an ASP adapter interface so the platform is not locked to one UAE accredited service provider.
Store submission payload hash, external reference, status, rejection reason, timestamps and retries.
Do not treat a PDF or emailed invoice as the final e-invoice integration model.

17. MVP Acceptance Criteria
A business can create a tenant, branch, users, parties and items.
An authorized user can create and post a sales invoice with correct VAT and balanced journal entries.
A payment can be received and allocated partially or fully to an invoice.
Posted records are immutable and can only be corrected through reversal or credit note.
The system produces party statements, trial balance, P&L, balance sheet and VAT summary from posted data.
Mobile can create permitted records offline and sync without duplication.
No user can access another tenant’s data in automated tenant-isolation tests.
Invoice PDF and thermal receipt are generated from the same canonical invoice data.
Backups, audit logs, monitoring and a tested restore procedure exist before production launch.
18. Development Rules
No controller may write directly to accounting tables.
Only the Ledger Posting Service can create posted journal entries.
No FLOAT or DOUBLE for currency or quantities requiring exact decimal handling.
No hard-coded VAT logic inside UI components or controllers.
No delete operation for posted financial documents.
No cross-tenant query without enforced tenant context.
No external notification or ASP request inside the invoice database transaction; use an outbox/job.
No production schema changes outside versioned migrations and reviewed deployment pipelines.
Every critical mutation must create an audit record and carry a correlation ID.
